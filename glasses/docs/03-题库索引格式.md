# qbank.idx 格式规范与实测数据

PC 端 `tools/build_qbank.py` 编译，眼镜端 `quiz/QBankStore.kt` 读取。两侧算法与常量必须一致。

## 为什么不用 SQLite

- 眼镜是 **Android Go** 设备，FTS5 在部分固件上不可用；FTS4 的中文分词需要自带 tokenizer；
- 题库是**只读**资产，编译期就能把倒排表建好，运行时只需一次 `readBytes()`（本库 0.91 MB）
  和若干二分查找，不需要 DB 引擎、事务、JNI；
- 换题库 = 换一个文件（`adb push` 到 `/sdcard/Download/qbank.idx` 即可热替换）。

## 归一化（两侧必须逐字一致）

`NFKC → lowercase → 只保留 Character.isLetter(ch) || ch in '0'..'9'`
（Python 侧：`ch.isalpha() or "0" <= ch <= "9"`）

标点、空白、符号全部丢弃；代理对（BMP 外字符）丢弃。目的：OCR 出来的全角/半角、
中英文标点、空格差异全部吸收，只留汉字与数字。

## 检索算法

对题干建 **汉字二元组（bigram）倒排**，查询时分两段打分：

```
score1 = Σ idf(命中的 bigram) / Σ idf(查询中所有 bigram)      # IDF 加权查询覆盖率
score2 = |题干bigram ∩ 查询bigram| / |题干bigram|              # 题干包含度（抗多字噪声）
final  = (1 - 0.6) * score1 + 0.6 * score2                    # alpha = 0.6
```

- 先用 `score1` 线性选出 top-40 候选（N=6622 只需一次 6622×40 的选择，不必全排序）；
- 只对候选算 `score2` 并重排，返回 top-3 给 UI（双击轮换）。
- `idf = ln(1 + N/df)`，出现越少的二元组权重越高，"的/是/为"这类高频词自动降权。

`alpha` 的取值是实测出来的（见下表）：纯 `score1`（alpha=0）在"题干+选项整卡入镜"时
只有 84.5%，加上 `score2` 后升到 97.5%~99.5%。

## 文件布局（全部 little-endian）

```
header 64 B
  0   char[4]  magic = "OQSY"
  4   u32      version = 1
  8   u32      nQuestions
 12   u32      nTerms
 16   u32      postingBytes
 20   u32      textBytes
 24   u32      offTerms      → u32[nTerms]        已排序 bigram key = (c1<<16)|c2
 28   u32      offTermPost   → u32[nTerms+1]      每个 term 的 postings 起止偏移
 32   u32      offPostings   → varint 序列        docId 差值（delta）编码
 36   u32      offTexts      → UTF-8 文本池       stem / answer / subject 共用
 40   u32      offDocs       → doc[n] × 28 B
 44   u32      docStride = 28
 48…63         reserved

doc 记录 28 B
  0  u32 stemOff    4  u32 stemLen
  8  u32 ansOff    12  u32 ansLen
 16  u32 subjOff   20  u32 subjLen
 24  u8  typeCode  25…27 pad     (1 单选 2 多选 3 判断 4 填空 5 简答 0 其他)
```

- `postings` 用 delta + varint：6622 题共 114 884 B，平均每题每 term 不到 1 B。
- bigram key 落在 u32 空间，可出现负数（`c1 ≥ 0x8000` 时），按位模式比较/排序仍然正确，
  Kotlin 侧用 `Int` 直接二分。

## 踩过的坑：term 表必须按**无符号**比较

`bigram key = (c1 << 16) | c2`。当 `c1 >= 0x8000` 时（Unicode 0x8000 以上的汉字，本库占 **19%**），
key 会落进 32 位有符号的负数区间。

- 编译端（Python）的 `sorted()` 按**无符号**升序排列；
- 读取端若用 Kotlin 的 `Int` 直接 `compareTo` 做二分，就是**有符号**比较，
  负数段整体错位 → 二分找不到或找到错误位置。

实测：有符号二分对真实题干 bigram 的查找成功率只有 **67%**（丢了 33%）。
症状极具迷惑性——**OCR 有字数、界面却没有答案**，因为分数被压到阈值以下。

修复（`QBankStore.termOffset`）：

```kotlin
val cmp = (v.toLong() and 0xFFFFFFFFL).compareTo(key.toLong() and 0xFFFFFFFFL)
```

为此增加了启动自检 `QBankStore.selfCheck()`：拿第 0 条题干原文检索自身，
不通过就在调试页直接显示「自检 失败」，不用再对着现象猜。

## 实测数据（6622 题，2026 公路水运试验检测题库）

| 指标 | 值 |
|---|---|
| 索引大小 | **955 004 B（0.91 MB）** |
| 不同 bigram 数 | 13 616 |
| postings 字节 | 114 884 |
| 文本池 | 545 708 |
| doc 表 | 185 416 |
| 查询耗时（PC / Python 参考实现） | 0.6~1.0 ms |
| 眼镜端预估 | 5~10× 于 PC，约 5~10 ms（待真机核对） |

准确率（300 条随机真题，查询 = 题干 + 全部选项）：

| 场景 | top1 | top3 |
|---|---|---|
| 干净文本 | 99.5% | 100% |
| 题干+选项整卡 | **98.0%** | 100% |
| 模拟 OCR 噪声（随机丢 7% 字符 + 插 5% 噪声） | 86.0% | 92.0% |

结论：**匹配算法不是瓶颈，OCR 质量才是**。丢字率一旦超过 5%，准确率掉得比加大 top-K 更快，
所以工程上优先保证：拍摄距离、对焦、光照、JPEG 质量（100）、`CAPTURE_MODE_MAXIMIZE_QUALITY`。

## 用法

```bash
# 编译（会打印统计；--self-test 跑噪声自检）
python tools/build_qbank.py --input ../../题库合并.json \
       --output GlassEyes/app/src/main/assets/qbank.idx --self-test

# 只统计不写文件
python tools/build_qbank.py --input ../../题库合并.json --report
```

输入兼容两种结构：`{"meta":{…},"questions":[…]}` 或裸数组 `[…]`。
字段读取：`stem`（题干）、`answerText` / `answer`（答案）、`subject`（科目）、`type`（题型）。
**只对题干建倒排**——选项与答案会把噪声带进索引，反而降低区分度。
